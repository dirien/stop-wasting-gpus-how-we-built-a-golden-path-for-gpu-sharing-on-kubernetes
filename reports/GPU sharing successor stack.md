# Upstream DRA now owns the GPU-sharing stack

The customer's platform needs extending, not replacing. As of October 31, 2026, its core (static MIG on A100, exposed through the NVIDIA DRA driver, with one shared ResourceClaim pinning several pods to slices on one physical GPU) is still the only fully supported, default-on sharing path. AWS recommends exactly this design for EKS. Everything more ambitious (DynamicMIG, ConsumableShares, MPS and time-slicing through DRA) is still Alpha. What has changed in the past year sits around that core. The NVIDIA DRA driver is now a Kubernetes SIG project on SemVer (v0.5.1, Oct 12, 2026) with a renamed chart. Kubernetes 1.37 made Workload/PodGroup gang scheduling and PodGroup-shared ResourceClaims Beta, both still off by default. Kueue has become the upstream-blessed quota layer, with MIG-aware counter quota. The inference world settled on the Gateway API Inference Extension plus llm-d 1.0 (Oct 20, 2026) under KServe. The future-proof successor stack is therefore kube-scheduler plus Kueue for admission and quota, KServe/vLLM behind a GAIE InferencePool for serving, in-cluster admission policy layered under the Pulumi policy pack, and dcgm-exporter ≥4.8.4 feeding profile-weighted chargeback. It is not "KAI + Grove", which the current deck presents as the next step. The deck has to change in four places: it cites a utilization study that cannot be found, it pins a DRA driver version and chart that no longer exist upstream, it presents an NVIDIA-steered Sandbox scheduler as the default next step, and it calls Grove alpha when it went beta the day before this report.

## The customer's MIG-plus-DRA core is still the supported centre

This section covers the partitioning layer and asks whether anything should replace the customer's MIG-plus-DRA foundation. The answer is no. The NVIDIA driver's governance moved: NVIDIA announced the donation at KubeCon EU 2026 ([NVIDIA blog](https://blogs.nvidia.com/?p=91716)). **v0.4.0 (May 15, 2026) was the first release "as a part of a Kubernetes SIG community."** It switched from CalVer to SemVer and moved the repo, Go module, image and chart to `registry.k8s.io`. The chart was renamed from `nvidia-dra-driver-gpu` to `dra-driver-nvidia-gpu`, and upgrades need `--version 0.4.0` plus `nameOverride=nvidia-dra-driver-gpu` to keep resource names ([v0.4.0 release](https://github.com/kubernetes-sigs/dra-driver-nvidia-gpu/releases/tag/v0.4.0)). Later releases are v0.4.1 (Jun 30), v0.5.0 (Aug 19) and **v0.5.1 (Oct 12, 2026)**. v0.5.0 added multi-user MPS, Fabric Manager partitioning and cross-namespace sharing via consumable capacity. It also stopped the driver injecting time-slicing implicitly ([v0.5.0](https://github.com/kubernetes-sigs/dra-driver-nvidia-gpu/releases/tag/v0.5.0)). v0.5.1 fixed a bug where "certain MIG profiles do not get the CI profile with the most multiprocessors" ([v0.5.1](https://github.com/kubernetes-sigs/dra-driver-nvidia-gpu/releases/tag/v0.5.1)). The NGC catalog still shows v0.4.1 as "Latest Tag" while also hosting v0.5.x images ([NGC](https://catalog.ngc.nvidia.com/orgs/nvidia/-/containers/dra-driver-nvidia-gpu/v0.5.1)). Pin versions from the GitHub releases, not from NGC.

Every sharing feature beyond static MIG is opt-in Alpha, and several of them cannot be enabled together. **DynamicMIG destroys partitions the driver did not create** when the plugin starts. It cannot be combined with MPS, NVML health checks or passthrough. On Ampere it cannot toggle MIG mode without a GPU reset, so with MIG mode on, full-GPU claims (including monitoring claims) cannot land on that GPU ([MIG guide](https://dra-driver-nvidia-gpu.sigs.k8s.io/docs/guides/gpu-allocation/mig/)). The v25.12.0 notes said outright that "A100 isn't supported" for dynamic MIG ([v25.12.0](https://github.com/kubernetes-sigs/dra-driver-nvidia-gpu/releases/tag/v25.12.0)). The current docs describe Ampere behaviour, so A100 support for DynamicMIG is **conflicting and unverified**. Treat DynamicMIG as an H100-and-newer pilot. ConsumableShares lets *independent* claims, even claims in different namespaces, share one GPU or MIG device. The docs are blunt that "capacity is scheduling accounting, not runtime isolation": a memory request does not cap CUDA memory ([consumable capacity guide](https://dra-driver-nvidia-gpu.sigs.k8s.io/docs/guides/gpu-allocation/consumable-capacity/)). AWS's own comparison labels dynamic MIG, MPS and time-slicing through DRA as Alpha. It recommends "static configuration with the DRA driver or the device plugin" for MIG, and it excludes DRA from EKS Auto Mode ([EKS docs](https://docs.aws.amazon.com/eks/latest/userguide/device-management-nvidia-dra-device-plugin.html)).

The GPU Operator changed install modes. **v26.7.0 (Aug 21, 2026) deploys the DRA driver through a new `GPUCluster` CR, and "a cluster cannot use `GPUCluster` and `ClusterPolicy` at the same time."** It requires K8s ≥1.34.2, driver ≥580 and CDI. v26.7.2 (Oct 14) bundles DRA driver v0.5.1 ([GPU Operator 26.7 notes](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/release-notes.html)). The customer runs GPU Operator v26.3.1 in `ClusterPolicy` mode with a separately Helm-installed driver, so moving to 26.7 is a migration project rather than a version bump.

Upstream, the primitives that would let sharing go beyond static MIG are on a visible GA track. Partitionable devices (KEP-4815) and consumable capacity (KEP-5075) have been Beta and on by default since 1.36, and both target Stable in 1.38 ([KEP-4815](https://github.com/kubernetes/enhancements/blob/master/keps/sig-scheduling/4815-dra-partitionable-devices/kep.yaml); [KEP-5075](https://github.com/kubernetes/enhancements/blob/master/keps/sig-scheduling/5075-dra-consumable-capacity/kep.yaml)). Kubernetes 1.37 made DRA extended-resource mapping GA, which lets legacy `nvidia.com/gpu` specs be served by a DRA driver "with no ResourceClaim needed". Device taints and `ResourceClaim.status.devices` also went GA in 1.37. Device Compatibility Groups (KEP-5963, Alpha) reject incompatible MIG-vs-vGPU combinations at scheduling time ([K8s 1.37 DRA blog](https://kubernetes.io/blog/2026/09/03/kubernetes-v1-37-dra-updates/)). The 1.38 stable targets are kep.yaml intentions, not shipped facts.

|---|---|---|---|---|---|
| NVIDIA DRA driver | kubernetes-sigs | v0.5.1 (Oct 12, 2026) | Native; static MIG default-on, everything else Alpha | NVIDIA hardware, SIG-governed | Keep; the core of the stack |
| NVIDIA GPU Operator | NVIDIA | v26.7.2 (Oct 14, 2026) | Bundles driver via `GPUCluster` | NVIDIA | Keep; plan the `ClusterPolicy`→`GPUCluster` migration |

HAMi has been CNCF Incubating since July 2026 ([CNCF blog](https://www.cncf.io/blog/2026/07/15/hami-becomes-a-cncf-incubating-project/)). It remains the broadest software-slicing layer, but v2.10.0 removed DRA components from its main chart ([HAMi v2.10.0](https://github.com/Project-HAMi/HAMi/releases/tag/v2.10.0)). Adopting it would add a second, non-DRA control plane. AMD shipped its GA-labelled DRA driver v1.0.0 on May 20, 2026 ([v1.0.0](https://github.com/ROCm/k8s-gpu-dra-driver/releases/tag/v1.0.0)). Its main-branch AutoPartition design builds dynamic partitioning purely from upstream shared counters, consumable capacity and taints ([driver-attributes.md](https://github.com/ROCm/k8s-gpu-dra-driver/blob/main/docs/driver-attributes.md)). That makes it the clearest proof that the DeviceClass/ResourceClaim contract is vendor-portable. It is unverified whether AutoPartition ships in a tagged release. The EFA DRA driver pairs EFA interfaces and accelerators by PCIe topology. AWS recommends it on managed node groups, but still recommends the device plugin with Karpenter and Auto Mode ([AWS What's New](https://aws.amazon.com/about-aws/whats-new/2026/05/kubernetes-dra-elastic-fabric-adapter/)).

## Kueue, not KAI, is the upstream-aligned next step for scheduling

The deck's "next step" slide should change most. Kubernetes 1.37 moved **Workload/PodGroup gang scheduling, workload-aware preemption and PodGroup-shared DRA ResourceClaims (`DRAWorkloadResourceClaims`, KEP-5729) to Beta**. The release blog adds: "Both Beta and Alpha features here are disabled by default and require manual enablement." GA is targeted for 1.38. The same post names Kueue as the layer that becomes "fully WAS-aware", which "long term … could use WAS as its engine for gang scheduling and topology-aware placement". KAI and Volcano are not mentioned ([K8s 1.37 WAS blog](https://kubernetes.io/blog/2026/09/08/kubernetes-v1-37-advancing-workload-aware-scheduling/)). The workload controllers already emit the upstream objects. JobSet v0.13.0 (Oct 12) creates native Workloads with shared DRA claims behind an alpha gate ([JobSet v0.13.0](https://github.com/kubernetes-sigs/jobset/releases/tag/v0.13.0)). LWS v1.0.0 (Oct 16) supports native PodGroup gangs, still opt-in ([LWS v1.0.0](https://github.com/kubernetes-sigs/lws/releases/tag/v1.0.0)). Managed control planes generally do not expose off-by-default Beta gates, so native gang scheduling on EKS is realistically a 1.38 story. EKS 1.37 availability and gate policy were not verified.

**Kueue v0.20.4 (Oct 29, 2026)** keeps kube-scheduler in charge of allocation and adds quota, borrowing, fair share and MultiKueue on top. v0.20.0 required migrating to the v1beta2 API ([Kueue v0.20.0](https://github.com/kubernetes-sigs/kueue/releases/tag/v0.20.0)). Its DRA support is the most explicit of any queueing project. ResourceClaimTemplates are Beta, and DRA-backed extended resources and partitionable devices are Beta and on by default since v0.19. **Counter-based quota (charging `consumesCounters`) is the recommended model for MIG** ([Kueue DRA docs](https://kueue.sigs.k8s.io/docs/concepts/dynamic_resource_allocation/)). Red Hat ships a supported build (1.4.1, based on Kueue 0.18) and describes DRA quota with borrowing, preemption and fair sharing ([Red Hat Developer](https://developers.redhat.com/articles/2026/10/02/smarter-gpu-sharing-how-red-hat-build-of-kueue-works-with-dynamic-resource-allocation)). For a European OEM, that gives a commercial support path outside a GPU vendor.

There is a catch the talk should address directly. Kueue's docs state: **"Direct `ResourceClaim` references in the Pod spec are not supported and will result in inadmissible workloads,"** and "device `constraints` (MatchAttribute) and per-request `config` are not supported" ([Kueue DRA docs](https://kueue.sigs.k8s.io/docs/concepts/dynamic_resource_allocation/)). The customer's signature pattern breaks on both counts: one pre-created `shared-mig-claim` with a `matchAttribute` constraint that lands three slices on one physical GPU. The way forward is upstream: KEP-5729 lets a PodGroup declare one claim template whose single claim all member pods share ([K8s 1.37 WAS blog](https://kubernetes.io/blog/2026/09/08/kubernetes-v1-37-advancing-workload-aware-scheduling/)). That is the customer's pattern, formalised. Until Kueue supports constraints on that path, teams must choose between Kueue quota (templates without matchAttribute) and the hand-built co-location claim. Volcano's capacity-plugin design covers both direct claims and templates, but it is a design document whose shipped status was not confirmed ([Volcano design](https://github.com/volcano-sh/volcano/blob/master/docs/design/capacity-dra-support.md)).

KAI Scheduler is a serious option, but it should not be presented as the default. It is **CNCF Sandbox** (the vote passed and the issue closed Feb 8, 2026 ([cncf/sandbox #372](https://github.com/cncf/sandbox/issues/372))). It is pre-1.0, and its LTS line is v0.18.x (v0.18.0 Sep 23, v0.18.6 Oct 15, 2026), supported until September 2027 ([KAI SUPPORT.md](https://github.com/kai-scheduler/KAI-Scheduler/blob/main/SUPPORT.md)). The repo has moved from `NVIDIA/KAI-Scheduler` to `kai-scheduler/KAI-Scheduler` ([KAI releases](https://github.com/kai-scheduler/KAI-Scheduler/releases)). **"DRA is disabled by default"** and must be switched on with a feature gate on both scheduler and binder ([KAI DRA docs](https://github.com/kai-scheduler/KAI-Scheduler/blob/main/docs/dra/README.md)). Its fractional GPUs use `gpu-fraction`/`gpu-memory` annotations, not DRA, and the default mode enforces no memory limit ([KAI GPU sharing](https://github.com/kai-scheduler/KAI-Scheduler/blob/main/docs/gpu-sharing/README.md)). Support for the upstream Workload API is an open, blocked issue ([KAI #1343](https://github.com/kai-scheduler/KAI-Scheduler/issues/1343)). Its own v0.18.0 fixes include "negative idle GPUs when one DRA claim is shared by several pods" ([KAI v0.18.0](https://github.com/kai-scheduler/KAI-Scheduler/releases/tag/v0.18.0)), which is precisely the customer's pattern. The landscape also shifted: **NVIDIA open-sourced the full Run:ai platform on Oct 13, 2026** (UI, CLI, API, scheduler and GPU Fractioning Operator) ([Techstrong.ai](https://techstrong.ai/articles/nvidia-hands-runai-to-the-open-source-community/)). With SchedMD's Slinky also described as "now part of NVIDIA" ([slurm-users](https://groups.google.com/g/slurm-users/c/k03FWLE-0g4)), NVIDIA now controls two of the main non-upstream scheduling paths.

| Project | Status | Latest (date) | DRA | Upstream WAS alignment | Fit |
|---|---|---|---|---|---|
| kube-scheduler + WAS | Kubernetes core | 1.37 (Aug 26, 2026) | Native | Is the standard (Beta, off by default) | Default; enable gang features at GA |
| Kueue | kubernetes-sigs | v0.20.4 (Oct 29, 2026) | Templates/extended resources Beta; no direct claims or matchAttribute | Explicitly the WAS-aware layer | Recommended quota layer |
| KAI Scheduler | CNCF Sandbox, pre-1.0 | v0.18.6 LTS (Oct 15, 2026) | Off by default; hardening | Not integrated | Optional, on a dedicated node pool |
| Volcano | CNCF Incubating (2022) | v1.16.0 (Oct 14, 2026) | DRA scoring; quota by design; KEP-5004 support open ([#6193](https://github.com/volcano-sh/volcano/issues/6193)) | Own PodGroup | Weaker fit; replaces the scheduler |
| Apache YuniKorn | Apache TLP | v1.10.0 (Oct 6, 2026) | Undocumented | None | Not a fit |

Running several schedulers on one cluster is risky. Each keeps its own cache of DRA allocations, so two schedulers allocating from the same ResourceSlices can double-book a device. Quota is also bypassed if Kueue and KAI queues run side by side without an integration (inference from the release notes above). If KAI is used, it belongs on its own tainted node pool, pinned to v0.18 LTS.

## Inference has converged on the Gateway API Inference Extension, llm-d and KServe

The talk promises teams can "run and serve models yourself." The serving layer now has a clear standard shape. **InferencePool `inference.networking.k8s.io/v1` is GA, and in GAIE v1.6.0 the Endpoint Picker, BBR and latency predictor moved into the llm-d repository** ([GAIE releases](https://github.com/kubernetes-sigs/gateway-api-inference-extension/releases); [InferencePool docs](https://gateway-api-inference-extension.sigs.k8s.io/api-types/inferencepool/)). The latest is v1.6.2 (Sep 17, 2026). Conformant gateways are Istio ≥1.28, Agentgateway, NGINX Gateway Fabric, Higress and Alibaba ACK ([implementations](https://gateway-api-inference-extension.sigs.k8s.io/implementations/gateways/)). Envoy Gateway and kgateway are absent from the current list, so check that before promising them. **llm-d v1.0.0 shipped Oct 20, 2026.** It is a CNCF Sandbox project since Mar 24, 2026, has over 500 contributors from 25+ organisations, and offers multi-tenant flow control, router HA, P/D disaggregation via LWS DisaggregatedSet and a DRA/DRANET topology guide ([IBM Newsroom](https://newsroom.ibm.com/2026-10-20-llm-d-1-0-advances-open,-cost-efficient-ai-inference-for-production-scale); [llm-d releases](https://github.com/llm-d/llm-d/releases)). Its image matrix spans NVIDIA, AMD, Intel XPU, TPU and CPU. The CNCF frames it as "a truly neutral standard", with Mistral AI among the contributors ([CNCF blog](https://www.cncf.io/blog/2026/03/24/welcome-llm-d-to-the-cncf-evolving-kubernetes-into-sota-ai-infrastructure/)). The 5–11.5x cost-reduction figures in the launch are vendor-reported and unverified.

**KServe (CNCF Incubating since Nov 2025) v0.20.0 (Aug 6, 2026)** turns LLMInferenceService into an llm-d-based platform. It also adds *managed DRA*: the `serving.kserve.io/dra-device-class` and `dra-gpu-count` annotations generate ResourceClaimTemplates for single-node and LWS multi-node deployments ([KServe 0.20 blog](https://github.com/kserve/website/blob/main/blog/2026-08-06-KServe-0.20-release.md)). Two caveats apply. KServe 0.20 pins llm-d v0.8.0 and GIE v1.5.0, behind llm-d 1.0. And managed DRA has no documentation beyond the CRD reference ([kserve/website #733](https://github.com/kserve/website/issues/733)), so whether it accepts a `mig.nvidia.com` DeviceClass is unverified.

The NVIDIA stack is open source but steered by NVIDIA. **Dynamo v1.6.0 (Oct 21, 2026) is the first Dynamo Enterprise Support release** ([Dynamo notes](https://docs.nvidia.com/dynamo/v1.6.0/reference/releases)). **Grove v0.2.0-beta1 (Oct 30, 2026) promoted its APIs to `grove.io/v1beta1`** ([Grove release](https://github.com/ai-dynamo/grove/releases/tag/v0.2.0-beta1)). Dynamo's install guide still says to upgrade Grove in lockstep "while the Grove APIs remain unstable" ([Dynamo install](https://docs.nvidia.com/dynamo/v1.6.0/kubernetes/installation/install-dynamo)). Both target multi-node, NVLink-scale disaggregated serving, which an 8×A100-40GB node carved into MIG slices does not need. NIM Operator 3.1.2 is the only stack found with documented DRA + MIG support ([NIM 3.1.2 DRA](https://docs.nvidia.com/nim-operator/3.1.2/dra.html)). The unversioned "latest" page still calls NIM DRA "a Technology Preview … not suitable for deployment in production" ([NIM latest](https://docs.nvidia.com/nim-operator/latest/dra.html)), and production use ties the OEM to NIM containers and NVIDIA AI Enterprise licensing.

The practical fit is clear. A plain vLLM or KServe pod on a 1g.5gb, 2g.10gb or 3g.20gb slice is the direct successor to the customer's PyTorch-on-MIG pods. MIG slices have no NVLink between them, so tensor parallelism across slices is not viable. That limits slices to small quantized LLMs and classic perception or quality-inspection models (inference from [PremAI guide](https://blog.premai.io/deploying-llms-on-kubernetes-vllm-ray-serve-gpu-scheduling-guide-2026)). llm-d's P/D disaggregation and wide expert parallelism only pay off once whole-GPU pools exist.

## Platform guardrails and chargeback still need in-cluster pieces

**The CNCF Kubernetes AI Conformance program had 31 certified platforms by March 24, 2026, including EKS and OVHcloud** ([CNCF](https://www.cncf.io/announcements/2026/03/24/cncf-nearly-doubles-certified-kubernetes-ai-platforms/)). Its v1.36 checklist makes gang scheduling, accelerator metrics, accelerator-aware autoscaling, an inference gateway and secure accelerator access MUST requirements. `gpu_sharing` and DRA-based driver management are only SHOULD ([AIConformance-1.36.yaml](https://raw.githubusercontent.com/cncf/ai-conformance/main/docs/AIConformance-1.36.yaml)). Conformance therefore does not guarantee MIG portability, and DeviceClass/ResourceClaimTemplate stays the portable contract. That contract behaves the same on EKS, AKS ([AKS blog](https://blog.aks.azure.com/2026/03/03/multi-instance-gpu-with-dra-on-aks)) and OpenShift 4.21, where DRA is GA ([Red Hat](https://developers.redhat.com/articles/2026/03/25/dynamic-resource-allocation-goes-ga-red-hat-openshift-421-smarter-gpu)). Every hyperscaler excludes DRA from its most-managed mode. For sovereignty, the AWS European Sovereign Cloud's only confirmed GPU is G6/L4 ([AWS](https://aws.amazon.com/about-aws/whats-new/2026/05/amazon-ec2-g6-aws-european-sovereign-cloud/)). L4 has no MIG, so moving there today would lose the hardware partitioning the talk depends on. For autoscaling, Karpenter's DRA support is Alpha and does not mention MIG ([karpenter.sh](https://karpenter.sh/docs/tasks/dra/)), and Cluster Autoscaler 1.36 added partitionable-device support ([CA 1.36.0](https://github.com/kubernetes/autoscaler/releases/tag/cluster-autoscaler-1.36.0)). On a fixed Capacity Block, a static managed node group stays correct.

The Pulumi policy pack is a good shift-left guard, but it is not enough alone. It only sees resources deployed through Pulumi. ResourceClaims created at runtime by users, Kubeflow, Kueue or KServe's managed DRA bypass it. No ready-made Kyverno or Gatekeeper policies for ResourceClaims were found. The robust pattern is admin-owned DeviceClasses as the MIG catalog, plus CEL ValidatingAdmissionPolicy on `resource.k8s.io` claims and templates, with Kyverno PolicyReports for audit evidence ([Kyverno VAP reports](https://kyverno.io/docs/policy-reports/validatingadmissionpolicy-reports/)). AWS also warns that `nvidia.com/mig.config` labels show the last *requested* layout, not live state ([EKS docs](https://docs.aws.amazon.com/eks/latest/userguide/device-management-nvidia-dra-device-plugin.html)). Policy should therefore check what the driver publishes, not node labels. If DynamicMIG ever replaces static MIG, layouts move from IaC-visible node config to claim time, and admission policy becomes mandatory.

On observability, **dcgm-exporter 4.8.4 (Sep 18, 2026) attributes DRA MIG metrics to pods, refreshes on ResourceSlice changes, and adds `pod_uid` and `GPU_CI_ID` labels**. The 4.8.3-era release added DRA ResourceSlice v1 support and renamed `Hostname` to `hostname`, which breaks existing dashboards ([dcgm-exporter releases](https://github.com/NVIDIA/dcgm-exporter/releases)). A GPU Operator 26.3.x preview did not expose the exporter's DRA ResourceSlice enrichment ([GPU Operator preview notes](https://nvidia.github.io/cloud-native-docs/review/pr-471/gpu-operator/latest/release-notes.html)), so the standalone chart can be the safer choice. Upstream, `ResourceClaim.status.devices` is Stable in 1.37 and resource health is Beta, while per-pool status (ResourcePoolStatusRequest) is Alpha ([K8s DRA observability](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/dra-observability/)).

Cost is the weakest layer. **OpenCost (CNCF Incubating) v1.121.0 (Jul 21, 2026) added per-model, per-token inference cost for vLLM/llm-d** ([CNCF blog](https://www.cncf.io/blog/2026/08/05/opencost-1-121-0-first-of-a-kind-kubernetes-inference-cost-tracking/)). No OpenCost or Kubecost documentation covers MIG slices or DRA claims, and Kubecost keys on `nvidia.com/gpu` requests ([Kubecost docs](https://www.ibm.com/docs/en/SSW0JQG_2.x/architecture/gpu-allocation.html)). DRA pods carry no such request, so these tools will likely book the whole GPU node as idle. That is an inference to confirm in a proof of concept. Vantage added MIG allocation on Oct 1, 2026, but only for the *single* strategy with GFD labels, and it does not mention DRA ([Vantage](https://www.vantage.sh/blog/kubernetes-nvidia-mig-gpu-cost-allocation)). The customer's infra uses `mig.strategy: mixed`. The workable chargeback today is self-built: dcgm-exporter per-MIG-instance metrics joined to team labels, weighted by profile slice fraction, priced from OpenCost node cost, and exported as FOCUS 1.3 split-cost rows ([FinOps.org](https://finops.org/insights/introducing-focus-1-3/)).

## The reference stack and the talk's corrected message

The recommended future-proof reference stack has six layers. Upstream components are preferred wherever they exist.

| Layer | Today (adopt) | Pilot | Defer / avoid |
|---|---|---|---|
| Partitioning | Static MIG via kubernetes-sigs DRA driver v0.5.1; K8s ≥1.36 | ConsumableShares for independent inference claims; DynamicMIG on H100+ pools only | DynamicMIG on A100; HAMi as a second control plane |
| Install | GPU Operator (drivers, MIG Manager, DCGM) | `GPUCluster` mode in 26.7.x as a planned migration | Mixing `ClusterPolicy` and `GPUCluster` |
| Scheduling and quota | kube-scheduler + Kueue v0.20.x with counter-based MIG quota | PodGroup-shared claims (KEP-5729) when EKS exposes them | KAI as the default; multiple schedulers on shared nodes |
| Serving | KServe InferenceService / vLLM on MIG behind a GAIE InferencePool (Istio ≥1.28 or Agentgateway) | llm-d 1.0 on whole-GPU pools | Dynamo/Grove/NIM unless serving NVLink-scale models |
| Guardrails | Pulumi policy pack + CEL ValidatingAdmissionPolicy on claims and templates + DeviceClass catalog | Kyverno PolicyReports | IaC-only enforcement |
| Observability and cost | dcgm-exporter ≥4.8.4, recording rules for profile-weighted slice-hours, OpenCost pricing | OpenCost 1.121 token cost; FOCUS 1.3 export | Request-based GPU cost tools as the source of truth |

The talk's message should move from "here is NVIDIA's next floor" to "here is why this design survives." Hardware partitions (MIG) are the isolation boundary. DRA's DeviceClass and ResourceClaimTemplate are the portable contract, and Kubernetes itself is absorbing gang scheduling and group-shared claims. Everything above, including quota, routing and cost, should speak that contract rather than vendor annotations. A replacement for the closing tagline: *"MIG isolates. DRA describes. Kueue admits. The gateway routes."* KAI, Grove and Dynamo still belong on the slide, as clearly labelled options for GPU-specific fairness or rack-scale serving, each with its maturity stated.

## Conclusion

Over the past year the customer's hand-built design has turned from a workaround into the upstream model. The shared claim becomes PodGroup-level claims, the MIG DeviceClass becomes Kueue counter quota, and the policy pack becomes admission policy on a portable contract. That makes the most defensible talk thesis the opposite of "adopt NVIDIA's next floor": the parts that last are the ones Kubernetes itself now standardises. The real near-term risk is not choosing the wrong scheduler. It is that the platform's signature move, one pre-created claim with `matchAttribute` co-location, is precisely what Kueue cannot yet admit. That tension, and how KEP-5729 resolves it, is the most honest and novel point the talk can make.

Commercially, a European OEM gets more neutrality from this stack than from any single vendor's. The upstream path has non-GPU-vendor support routes (Red Hat Kueue, CNCF-governed llm-d with European contributors), a multi-vendor hedge (AMD's v1.0 DRA driver uses the same primitives), and no NVAIE dependency for serving. The cost layer is the open gap. No major tool allocates DRA-backed MIG slices correctly yet, so profile-weighted, FOCUS-formatted chargeback built on dcgm-exporter is something the platform team can ship and the talk can show as new work.
